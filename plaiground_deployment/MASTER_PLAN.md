[DEPLOYMENT_PLAN.md](DEPLOYMENT_PLAN.md)(배포 전환)와 [directory_plan.md](directory_plan.md)(디렉토리 구조)를 하나의 실행 순서로 합친 문서다. **무엇을 언제 누가 하는지는 이 문서를 따르고**, 각 작업의 상세 체크리스트와 근거는 두 원본 문서를 본다.

## 0. 결론

**어느 한쪽을 먼저 끝내는 것이 아니다. 두 계획을 작업 단위로 풀어서 다시 묶는다.**

1. 디렉토리 계획의 **앞 절반(이동 전용, 1~4번)** 을 가장 먼저 한다. 같은 날 배포 계획의 **Phase 0(계정 만들기)** 을 병행한다.
2. 디렉토리 계획의 **뒤 절반(로직 변경, 5~7번)** 은 따로 하지 않는다. 배포 계획 **Phase 1과 같은 작업**이므로 하나로 합친다.
3. 그 뒤는 배포 계획의 순서를 그대로 따른다.

```
Stage A  (2일)     A1 폴더 이동 전용 ──────┐
                   A2 계정·조직 만들기 ────┤  병행
                                           ▼
         ── 관문: 이동이 main에 들어가고, 저장소가 조직으로 이전됨 ──
                                           ▼
Stage B  (2주)     B0 인터페이스 확정 (반나절, 같이)
                   B1 호스트 리팩터 ───────┐
                   B2 엣지 층 배포 ────────┤  병행
                                           ▼
Stage C  (1주)     터널로 공개, 전체 흐름 시연
                                           ▼
Stage D  (3~4주)   D1 멀티유저 격리 ───────┐
                   D2 파일럿 운영 준비 ────┘  병행
```

공개 URL에서 전체 흐름을 시연하기까지 약 3주 반, 학생 여러 명을 받을 수 있기까지 약 7~8주다. 두 사람이 파트타임으로 일한다는 가정의 추정치다.

## 1. 왜 이 순서인가

### 폴더 이동을 가장 먼저 하는 이유

- **이동 비용은 시간이 갈수록 커진다.** 지금은 테스트가 없고, 파일이 60개 남짓이고, 열려 있는 브랜치가 없다. 상협이 첫 브랜치를 딴 뒤에 폴더를 옮기면 그 브랜치의 모든 변경이 충돌한다.
- **Phase 1의 첫 작업이 곧 폴더 분리다.** "텔레메트리 SDK를 pip 패키지로 분리"는 `portfolio_demo/telemetry`를 `packages/telemetry`로 옮기는 일과 같다. 옛 구조에서 Phase 1을 하면 고친 뒤에 다시 옮기게 되어 같은 파일을 두 번 만진다.
- **경로가 다른 결정들의 입력이다.** Cloudflare Pages 빌드 디렉터리, 인터페이스 문서, 에이전트 지침 파일이 모두 경로를 적는다. 한 번 정하고 시작하는 편이 싸다.
- **상협이 구조를 한 번만 배운다.**

### 그렇다고 디렉토리 계획을 끝까지 먼저 하지 않는 이유

5~7번(서버 두 개 합치기, 설정 통합, 런타임 데이터 분리)은 **로직 변경**이고, 배포 계획 Phase 1의 항목과 하나씩 대응한다.

| 디렉토리 계획 | 배포 계획 Phase 1 | 합친 작업 |
|---|---|---|
| 6번 `settings.py`로 경로 통합 | 설정을 환경변수로 | 환경변수를 읽는 `settings.py` 하나 |
| 6번 런타임 데이터를 `var/`로 | 텔레메트리 기록 위치 분리, 레포 마운트 제거 | `var/` 아래 사용자별 워크스페이스만 마운트 |
| 5번 라우팅 표 하나로 | 인증 훅, `run` 경로 검증 | 라우팅 표 앞단에 인증과 검증을 한 번만 |
| 2번 telemetry 패키지 이동 | SDK를 휠로 만들어 이미지에 설치 | 이동은 Stage A, 휠 빌드는 Stage B |

따로 하면 같은 파일을 두 번 열고, 두 번 검증한다.

### 계정 만들기를 병행하는 이유

코드와 의존 관계가 전혀 없다. 게다가 가입 인증, 초대 메일 수락처럼 **기다리는 시간**이 있어서 일찍 시작할수록 좋다.

### "이동 먼저, 변경은 그다음"을 지키는 이유

이동과 로직 변경을 한 커밋에 섞으면 diff를 사람도 AI도 읽을 수 없다. 문제가 생겼을 때 원인이 이동인지 변경인지 가릴 수도 없다. 이동 전용 커밋은 "import 줄과 경로 문자열만 바뀌었는가"만 보면 검토가 끝난다.

## 2. Stage A — 기반 만들기 (2일)

### A1. 폴더 이동 전용 · 담당: 준형 · 약 5시간 · **완료 (2026-09-21, A1-5만 남음)**

브랜치 `restructure/stage-a1`. 계획과 달라진 점:
- 경로 상수 30여 개를 파일마다 다시 계산하는 대신 `paths.py` 두 개로 모았고, 런타임 데이터도 이때 `var/`로 옮겼다. 원래 B1-1과 B1-2의 일부였다. B1-1에는 환경변수 읽기, B1-2에는 사용자별 워크스페이스 디렉터리만 남는다.
- 점검 명령(A1-0)은 새 구조 기준으로 `scripts/check.py`에 만들었다. 이동 전 기준선은 기존 자체 점검을 직접 돌려 확인했다.
- `uv`가 설치되어 있지 않아 루트 `pyproject.toml`은 만들지 않았다. 설치는 `pip install -e packages/telemetry -e apps/host`.
- 컨테이너 이미지 폴더는 이미지 이름과 맞춰 `apps/host/docker/plaiground-base`로 유지했다. 이름을 바꾸면 이미지를 다시 빌드해야 한다.
- `web_demo/`의 화면 스펙 4개는 `PRODUCT.md`가 참조하고 있어 삭제하지 않고 `docs/specs/`로 옮겼다.
- `PRODUCT.md`는 루트에, `DESIGN.md`는 `apps/web/`에 두었다. 디자인 도구가 이 위치를 기준으로 찾는다.

GPU가 있는 PC에서 마지막 전체 흐름 확인을 해야 하므로 준형이 맡는다. 상세는 [directory_plan.md](directory_plan.md) 4장(목표 구조)과 5장(이동 순서).

| 순서 | 작업 | 확인 |
|---|---|---|
| A1-0 | **점검 명령 하나 만들기.** 이미 있는 자체 점검 함수(`demo()`) 9개 중 Docker가 필요 없는 것들과 `npm run build`를 한 번에 돌리는 스크립트 | 지금 구조에서 통과 |
| A1-1 | `web_demo/` 삭제, 구버전 정적 경로 제거 | 점검 명령 통과 |
| A1-2 | `portfolio_demo/telemetry` → `packages/telemetry`. 템플릿 4개의 import 줄 수정 | 점검 명령 통과 |
| A1-3 | 나머지를 `apps/host`, `apps/web`으로 | 점검 명령 통과 |
| A1-4 | 루트 `README.md`, `pyproject.toml`, **`CLAUDE.md`** 추가. 문서를 `docs/`로 옮기고 옛 경로 수정 | 점검 명령 통과 |
| A1-5 | 전체 흐름 수동 확인: Start AI → Web IDE → 학습 → 포트폴리오 → View AI | 전부 동작 |

A1-0을 맨 앞에 둔 이유: 이동 단계마다 GPU와 Docker를 띄워 전체 흐름을 돌릴 수는 없다. 1분 안에 끝나는 점검이 있어야 단계마다 확인할 수 있고, 이후 AI 에이전트가 자기 작업을 스스로 검증하는 수단도 된다.

주의:
- 학습 템플릿의 **의도된 버그 줄은 건드리지 않는다.** 바뀌는 것은 맨 위 import 줄뿐이다.
- `var/generated/`에 있던 기존 학습 스크립트(사용자가 직접 고친 것 포함)는 import 줄만 새 패키지 이름으로 바꿔 두었다. 다시 세팅하지 않아도 실행된다.

## 3. Stage B — 두 층을 동시에 (2주)

### B0. 인터페이스 확정 · 담당: 같이 · 반나절 · **완료 (2026-09-22, 회의 대신 문서로: decisions.md, docs/interface.md, supabase/migrations/, CONTRIBUTING.md)**

두 사람이 2주간 따로 일하려면 만나는 지점을 먼저 고정해야 한다. [DEPLOYMENT_PLAN.md](DEPLOYMENT_PLAN.md) 5장의 초안(테이블, 엔드포인트 이동 경로, 비밀 목록)을 확정해 `docs/interface.md`로 저장한다. 이 회의에서 아래 두 가지도 결정한다.

**결정 1 — 프론트의 API 호출을 한 곳으로 모은다.** 지금 `fetch` 15곳과 `EventSource` 2곳이 컴포넌트에 흩어져 있다. B1은 인증 헤더와 Gemini 키 헤더를, B2는 주소와 Supabase 전환을 같은 호출부에 넣어야 하므로 그대로 두면 두 사람이 같은 줄에서 충돌한다. `apps/web/src/api.js`에 호출 함수 하나를 만들고 모든 호출부를 그것으로 바꾸는 작업을 **B0 직후 엣지 담당이 가장 먼저** 한다.

**결정 2 — SSE를 `EventSource`에서 `fetch` 스트리밍으로 바꾼다.** `EventSource`는 요청 헤더를 설정할 수 없다. 환경 세팅(`/api/setup`)과 포트폴리오 생성(`/api/portfolio/run`) 두 곳이 이를 쓰는데, 둘 다 인증 토큰이 필요하고 후자는 Gemini 키까지 보내야 한다. 키를 URL 쿼리에 넣으면 서버 로그와 프록시에 남으므로 안 된다. `api.js` 안에서 `fetch`의 응답 스트림을 읽어 SSE를 해석하는 함수로 교체한다.

**결정 3 — API를 같은 주소 아래로 둘지.** Stage C에서 확인할 설계 항목이다. 4장 참고.

## 4. Stage C — Tailscale로 연결해 시연 (1주)

배포 계획 Phase 3. B1과 B2가 **둘 다** 끝나야 시작한다. 상세는 [DEPLOYMENT_PLAN.md](DEPLOYMENT_PLAN.md) 3장 Phase 3.

도메인 없이 0원으로 가기 위해 Cloudflare Tunnel·Access 대신 Tailscale을 쓴다. 호스트 PC의 API와 IDE를 tailnet 안에만 HTTPS로 열어 두 사람의 노트북에서 접속한다. 인터넷에는 노출되지 않는다.

- **SPA와 API의 주소가 다르다.** `pages.dev`와 `ts.net`이므로 B1-1의 허용 오리진 설정에 Pages 주소를 넣는다.
- **첫날 확인할 것.** 공개 사이트에서 사설 대역 주소를 호출할 때 크롬이 로컬 네트워크 접근 허용을 물을 수 있다. 직접 시험해 보지 못했다. 막히면 API만 Tailscale Funnel(공개 주소)로 바꾸고 B1-5의 JWT 검증에 맡긴다.
- **외부 사용자는 이 단계의 대상이 아니다.** Tailscale 무료 플랜은 비상업적 용도 한정이다. 파일럿 학생을 받는 시점에 도메인(연 1~2만 원대)을 사서 Cloudflare Tunnel로 바꾼다. 그때 고칠 코드는 없고 설정값만 바뀐다.

**완료 기준:** 상협이 자기 노트북에서 로그인부터 본인 Gemini 키로 포트폴리오 생성까지 마치고, 그 뒤 준형의 PC를 꺼도 포트폴리오가 열린다.

## 5. Stage D — 실사용 준비 (3~4주)

- **D1. 멀티유저 격리** · 호스트 담당 · 배포 계획 Phase 4. 사용자별 컨테이너, 이그레스 제한, 서버 서명. 개발과 검증은 준형의 PC에서 0원으로 한다.
- **D2. 파일럿 운영 준비** · 엣지 담당 · 배포 계획 Phase 5. 약관, 백업, 가동 확인, 유료 전환 점검.

**완료 기준:** [DEPLOYMENT_PLAN.md](DEPLOYMENT_PLAN.md) 6장의 보안 점검표를 두 사람이 같이 돌려 전부 실패함을 확인한다.

Stage D와 별개로, [STATUS.md](../docs/STATUS.md)에 남아 있는 기능 작업(llama·gemma에 View AI 기록기 연결, 대형 모델용 저장 방식)은 **Stage C 이후**로 미룬다. 구조와 배포가 흔들리는 동안 기능을 같이 늘리면 두 종류의 변경이 섞인다. 파일럿 상대에게 View AI 시연이 꼭 필요하다면 LoRA 두 모델 연결만 Stage C 직후에 넣는다.

## 6. AI 코딩 도구와 같이 일하기 위한 규칙

두 사람 모두 AI 코딩 도구를 쓴다면, 구조와 문서가 곧 그 도구에 주는 지시문이다. 아래는 비용이 거의 들지 않고 효과가 큰 것들이다.

1. **루트에 에이전트 지침 파일(`CLAUDE.md`)을 둔다.** 지금은 프로젝트 수준 지침이 없고, 중요한 규칙이 준형의 개인 설정에만 있다. 상협의 도구는 그 규칙을 모른다. 넣을 내용: 폴더 구조 한 장, 설치·실행·점검 명령, 그리고 금지 사항(학습 템플릿의 의도된 버그를 고치지 말 것, 구 저장소에 푸시하지 말 것, `service_role` 키를 프론트나 컨테이너에 넣지 말 것, 폴더 소유권).
2. **점검 명령 하나를 유지한다.** 도구가 자기 변경을 스스로 검증할 수 있어야 사람이 검토할 양이 준다. A1-0에서 만들고 B1-7에서 `pytest`로 키운다.
3. **계약을 파일로 둔다.** `docs/interface.md`와 `packages/telemetry/FORMAT.md`. 두 사람의 도구가 같은 파일을 읽어야 양쪽 구현이 어긋나지 않는다.
4. **이동 커밋과 변경 커밋을 나누고 PR을 작게 유지한다.** 큰 diff는 사람도 도구도 제대로 검토하지 못한다.
5. **비밀을 도구에 보이지 않는다.** `.env` 파일을 도구의 읽기 권한에서 제외하고, 키를 채팅에 붙여넣지 않는다. 디버깅에 키 값이 필요한 경우는 없다.
